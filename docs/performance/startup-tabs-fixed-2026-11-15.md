# 初回描画・タブ切り替えの修正と実測

2026-11-15。概要タブの反復停止は短縮した。起動時と分析パネル初回スクロールの停止は残っており、完全解消ではない。

## 実装

- 補足イベントが空なら履歴照合を直ちに終了。照合対象のない区間の検索用Mapも作らない。空入力でも全90日・1,000曲を処理していた概要の負荷を除いた。
- 日次差分では再生・スキップがどちらも増えていない曲の一時オブジェクトを作らない。文字列正規化の正規表現も再利用する。集計に含める条件は従来と同じ。
- 再生中画面をパネル単位のSliverListに変更。画面外の先行構築を省き、一度表示したパネルはKeepAliveで保持する。型と出現順のキー、findChildIndexCallbackで任意の通知パネル挿入時も状態を追跡する。歌詞展開を含む状態保持を回帰テストした。
- カレンダー用の履歴差分準備をFutureProviderへ移し、4msを目安にイベントループへ処理を譲る。準備中は進捗表示、失敗時は再試行できる。画面を離れた場合は以後の準備を中止する。1組の比較自体は同期処理なので4msは厳密な上限ではない。
- 先のローダー更新範囲の限定、二重アニメーションの除去、大きなプラットフォーム応答の変換分離も維持した。

OpusへClaude Code CLIから読み取り専用で2回相談した（利用記録はclaude-opus-5-5）。空イベント照合の無駄と、単純な遅延構築ではスクロール後にStateが失われる問題を確認し、状態保持を追加した。背景ぼかし除去の案は試したが、改善が確認できず採用していない。[相談記録](opus-startup-consultation-2026-11-15.md)

## 最終ビルドの比較

Windows実PC / i5-13400F / Chromium 157 / profileビルド / デモ1,000曲・90日分。スマートフォン幅390×844 CSS px、DPR 1。計測中は全件visibility=visible。ビルドやテストを終えてから実ブラウザーで操作した。

修正前は今回の追加修正前のローカルprofile成果物、修正後は最終ソースから再ビルド。修正前後を交互に起動し、双方3回採取。各ビルドを事前に開いている。起動は`loading_preview=1`による4秒の意図的な待機を含むため、総起動所要時間としては扱わない。時間帯で処理時間が大きく変動したため、以前の調査値から改善率を算出せず、最後の比較セットを以下に掲載する。
