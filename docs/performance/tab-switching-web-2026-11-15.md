# タブ切り替え実測 — 2026-11-15

引っ掛かりあり。優先して改善すべき箇所は概要の再表示と、概要内の分析パネル初回表示。

## 条件と測定方法

Windows実PC、Intel Core i5-13400F、Chromium 157、Flutter Web profileビルド。1,000曲・90日分のデモ履歴。前回起動計測と同じ修正後ビルドを使用。390×844と1024×768 CSS px、DPR 1。端末エミュレーションやCPUスロットリングは使用していない。iPhone/iPad実機の結果ではない。

初期表示完了後に実際のUIをクリックし、pointerdownから1秒間のrequestAnimationFrame間隔と50ms以上のlong taskを収集。タブの初回表示後、スマートフォン幅では各タブを3回再表示。タブレット幅は同一セッション内で幅を変更して確認したため、コールド表示ではない。スクロールは操作直前から1.5秒間。全操作中document visibilityはvisible。

rAF間隔はブラウザーの描画機会を示す代理指標で、Flutter/GPUフレーム時間やクリック応答時間そのものではない。通常の周期は約13.3ms。Flutter profileのBUILD/LAYOUTマーカーも併せて確認した。

概要の最初の下スクロール（分析パネルが表示領域に入る操作）で213.4ms、long taskは223msと128ms。次の下スクロールは39.9msでlong taskなし。常時スクロール全体が遅いという結果ではなく、初めて表示する内容に負荷が集中している。

内部の分類切り替えは比較的軽い。ランキングの歌手39.9ms・アルバム13.6ms・最近26.6ms、ライブラリのアーティスト40.0ms、カレンダーのアルバム39.9ms・アーティスト26.5ms。ランキング歌手だけ52msのlong taskを1件記録。他の分類切り替えには50ms以上のlong taskなし。各分類は1回の確認で、長時間・連続操作を網羅した結果ではない。

## 実装との照合

概要の再表示2回目では、約201msのLAYOUT内に約181.8msの単一BUILD区間がある。一方、そのフレームのPAINTは約1.6ms。少なくともこの停止は、見た目を描く処理より、レイアウト中の子ウィジェット構築に時間を使っている。マーカーはウィジェット名を含まないため、個別クラスへの帰属は未確定。

- `home_screen.dart` の `_StatsContent` / `_SectionBody` は選択タブの内容を置き換える。再表示で内容が再構築され、ライブラリのStateも作り直される構造。
- `overview_section.dart` の `_OverviewSliverSection` はSliverListを使っているが、画面内とその近傍のパネル構築は同期実行される。
- 同ファイルの `_SnapshotTrendChart.build` は毎回 `_snapshotTrendValues` を呼び、履歴間の差分を再計算する。`_SnapshotStatusPanel.build` も `history.latestDelta` を毎回取得する。
- `shared_helpers.dart` の `_snapshotTrendValues` は最大8区間について `listeningActivityDelta` を実行。分析・カレンダー側にも履歴からの集計があり、優先して個別計測すべき候補。今回の記録だけでこの関数が181.8ms全体の原因とは断定しない。

改善の順序は、概要の重いBUILDを個別計測し、データが変わらない再表示で集計を繰り返さないようにすること。その後に初回構築の分割・遅延を検討する。全タブを一括して保持する方式は起動時負荷とメモリーが増えるため、計測なしに適用しない。
